# RAG Knowledge Assistant

> 🇬🇧 [English version](README.md)

Демонстрационная **RAG-система** (Retrieval-Augmented Generation) с видением «как в продакшене»: чат-ассистент, отвечающий на вопросы по базе знаний с **гибридным поиском (векторный + BM25)**, **кликабельными цитатами**, **офлайн-оценкой качества** и веб-интерфейсом. В комплекте — справочник вымышленной компании «Небула» (русский + английский), демонстрирующий **кросс-язычный поиск**.

Акцент проекта — не «ещё одна обёртка над LangChain», а измеримое качество retrieval, честные инженерные компромиссы и воспроизводимые эксперименты.

## Возможности

- **Гибридный поиск** — dense-эмбеддинги (многоязычная E5) + разреженный BM25, слияние через **Reciprocal Rank Fusion (RRF)**
  - …с двумя осознанными, измеренными улучшениями: **отсечение кандидатов BM25 по относительному порогу** и **гарантия top-1 от каждого retriever'а** (см. «Решения и trade-offs»)
- **Цитаты** — каждый факт в ответе снабжён ссылкой на источник [n]; в интерфейсе видно текст чанка, его RRF-скор и ранги в dense/sparse выдачах
- **Кросс-язычный поиск** — вопрос на русском находит английский документ (и наоборот)
- **Работает с LLM и без** — любой OpenAI-совместимый API (OpenAI, Groq, OpenRouter, Ollama…). Без ключа — честный режим *retrieval-only* с экстрактивным ответом
- **Офлайн-оценка качества** — `python -m eval.evaluate` считает Recall@k / MRR для трёх режимов поиска на размеченном наборе; LLM не нужен, результаты воспроизводимы
- **Загрузка своих документов** — `.md`, `.txt`, `.pdf` через UI или API
- **FastAPI-бэкенд + фронтенд без зависимостей** — одна самодостаточная HTML-страница
- **Тесты, Docker, compose** — `pytest`, сборка контейнера одной командой с прогретой моделью

```
        │                                            │
        ▼                                            ▼

 (точный косинусный поиск)
        └───────────────┬────────────────────────────┘
                        ▼
       RRF-фьюжн + относительный порог BM25 + гарантия top-1
                        ▼
              top-k чанков (k = 2…8)
                        ▼
   ┌── LLM-ключ задан ─► ответ генерируется строго по контексту,
   │                     после каждого факта — цитата [n]

                         ближайшие к вопросу, с цитатами
```

## Оценка качества

Качество retrieval измеряется на 16 размеченных вопросах (`eval/questions.jsonl`), к каждому указан ожидаемый документ-источник. Поэтому **LLM для оценки не нужна**, а результаты детерминированы:

```bash
python -m eval.evaluate --mode hybrid    # или: vector | bm25
```

Замеры на корпусе этого репозитория (CPU, `multilingual-e5-base`):

| Режим поиска     | Recall@1 | Recall@3 | Recall@5 | MRR  |
|------------------|---------:|---------:|---------:|-----:|
| **hybrid**       | **0,94** | **1,00** | **1,00** | 0,96 |
| vector only      | 0,94     | **1,00** | **1,00** | **0,97** |
| BM25 only        | 0,69     | 0,75     | 0,75     | 0,72 |

Сравнение embedding-моделей (режим hybrid, тот же корпус):

| Модель                        | Recall@1 | Recall@5 | MRR  |
|-------------------------------|---------:|---------:|-----:|
| `multilingual-e5-small`       | 0,81     | 0,94     | 0,86 |
| `multilingual-e5-base` (default) | **0,94** | **1,00** | **0,96** |

Два вывода из экспериментов, которые сформировали код:

1. **Наивный RRF штрафует уникальные находки.** Документ с рангом #1 в dense-поиске, которого нет в выдаче BM25 (кросс-язычный запрос, нулевое лексическое пересечение), получал меньше очков, чем документ, найденный на средних местах обоими. Решение: top-1 каждого retriever'а всегда попадает в итоговую выдачу — Recall@5 вырос 0,94 → 1,00 без ущерба остальным запросам.
2. **BM25 требует стоп-слов и порога кандидатов.** «Голый» BM25 на русском ранжирует документы с совпадениями «на / и / сколько» выше релевантных, и это отравляет фьюжн. Стоп-слова + отсечение кандидатов ниже 0,35 от топ-скора решили проблему.

В продакшене я бы добавил кросс-энкодерный реранк поверх слитых кандидатов — слой retrieval спроектирован так, что это изменение на ~20 строк (см. «Дорожная карта»).

## Конфигурация

Все настройки — переменные окружения (см. `.env.example`):

| Переменная | По умолчанию | Назначение |
|---|---|---|
| `LLM_API_KEY` | *(пусто)* | Задан → генерируемые ответы с цитатами; пуст → экстрактивный режим |
| `LLM_BASE_URL` | `https://api.openai.com/v1` | Любой OpenAI-совместимый endpoint (Ollama: `http://localhost:11434/v1`) |
| `LLM_MODEL` | `gpt-4o-mini` | Название chat-модели |
| `EMBED_MODEL` | `intfloat/multilingual-e5-base` | Модель эмбеддингов Sentence-Transformers |
| `CHUNK_SIZE` / `CHUNK_OVERLAP` | `1100` / `200` | Параметры чанкинга (символы) |
| `TOP_K` / `CANDIDATES` | `4` / `12` | Возвращаемых чанков / кандидатов от каждого retriever'а |
| `RRF_K` | `60` | Константа сглаживания RRF |
| `SPARSE_REL_THRESHOLD` | `0,35` | Мин. скор BM25-кандидата как доля от лучшего |

## Решения и trade-offs

- **NumPy вместо FAISS/Qdrant.** На масштабе демо (тысячи чанков) точный brute-force косинус занимает единицы миллисекунд и убирает из деплоя целый сервис. Хранилище изолировано за интерфейсом `VectorStore`, поэтому переход на Qdrant/pgvector — изменение одного файла (что стоит сделать на ~100k+ чанков).
- **E5-модели требуют префиксов `query:` / `passage:`.** Они применяются централизованно в `embeddings.py`; без них качество заметно проседает.
- **Структурный чанкинг важнее модели.** Сплиттер предпочитает границы абзацев, затем предложений и слов; заголовок документа попадает в метаданные чанка. Качество нарезки — самый недооценённый фактор качества RAG.
- **Режим retrieval-only — это фича.** Демо полностью работоспособно без платного API, а экстрактивный fallback заодно служит честным режимом «покажи, что нашёл retriever» для отладки.
- **Оценка без LLM.** Вопросы размечены документом-источником, поэтому метрики retrieval дешёвые, детерминированные и пригодные для CI. LLM-оценка качества ответов (RAGAS) вынесена в дорожную карту.

## Дорожная карта

- Кросс-энкодерный реранк поверх кандидатов (`cross-encoder/mmarco-mMiniLMv2-L12-H384-v1`)
- Замена `VectorStore` на Qdrant; инкрементальная переиндексация отдельных документов
- Стриминг ответов (SSE), память диалога с переписыванием запроса
- RAGAS-метрики достоверности ответов в CI
- Query expansion / HyDE для коротких неоднозначных запросов
